# RAG 性能测试报告

测试时间：2026-08-09 15:43
测试工具：Node 脚本 `scripts/perf-test.js`（worker 池并发）
测试环境：本机（Java 21 / MySQL 8 / Chroma / 本地 bge-small-zh-v1.5 CPU / DeepSeek API）

| 场景 | 平均 | P50 | P95 | 最大 | QPS |
|------|-----:|----:|----:|-----:|----:|
| 混合检索（本地，无重排） | 31.8ms | 33ms | 36ms | 36ms | 31.4 |
| 混合检索 + LLM 重排 | 833ms | 794ms | 989ms | 989ms | 1.2 |
| Chat 问答（客户端视角） | 3692ms | 3403ms | 4984ms | 4984ms | 0.3 |
| Chat 问答（服务端 elapsedMs） | 3689ms | 3400ms | 4982ms | - | - |

说明：chat 的服务端耗时 ≈ 客户端耗时，即网络开销可忽略；
3690ms 中约 3600ms 是 DeepSeek 生成/重排时间，本地检索仅约 30ms。

## 结论

1. 本地检索链路性能优秀（~30ms），RAG 工程实现（MySQL 全文 + Chroma + RRF）无性能短板。
2. 当前吞吐瓶颈是本地 Embedding 推理（单进程 CPU），与 Java 后端无关。
3. LLM 重排 +800ms 延迟，换取 Top-1 命中率 65% → 87.5%（+22.5pp），性价比很高。
4. Chat 总延迟的 ~95% 来自 DeepSeek 生成，符合 RAG 应用的典型画像；SSE 首字 ~2.2s 可用。
5. 全部测试 0 错误，稳定性良好。

## 优化建议（按性价比）

1. Embedding 服务多 worker：`uvicorn --workers 2`（注意：多进程会复制模型，内存约翻倍）。
2. 或切换到 SiliconFlow bge-m3 API Embedding（并发能力强且模型更强），本地服务仅作离线兜底。
3. 高频问题回答缓存（Cache-Aside）+ 检索 embedding 结果缓存。
4. 生产化时把重排与生成串行链路保持现状即可，避免为省 800ms 牺牲可解释性。
## 五、第一梯队优化实测（2026-08-09）

### 1. 热问题回答缓存（Redis Cache-Aside）✅ 收益最大
| 场景 | 延迟 |
|------|-----:|
| 首次提问（未命中） | 4.2-5.9s |
| 重复提问（命中缓存） | 17ms |

重复问题约 300 倍加速，且零 DeepSeek 调用（省钱）。实现：问题 SHA-256 作为 key，
TTL 24h，命中时流式接口同样直接返回（citations + 全文 + done）。

### 2. Embedding 多 worker ⚠️ 收益有限
| 并发 | 1 worker（优化前） | 2 workers（优化后） |
|-----:|------------------:|--------------------:|
| 1 | 30.8ms / 32.5 QPS | 30.4ms / 32.9 QPS |
| 5 | 68.9ms / 14.5 QPS | 66.6ms / 15.0 QPS |
| 10 | 120.7ms / 8.3 QPS | 145.3ms / 6.9 QPS |
| 20 | 253.4ms / 3.9 QPS | 227.5ms / 4.4 QPS |

结论：无明显提升（高并发略好但 10 并发反而变差），确认瓶颈是 CPU 推理本身
（torch 多线程在进程间互相争抢）。配置项 EMBEDDING_WORKERS 保留；
真正解法是把 Embedding 放到 GPU/API（SiliconFlow 等）。

### 3. 本地重排（bge-reranker-base）✅ 可作离线备选
| 指标 | LLM 重排 | 本地重排 |
|------|---------:|---------:|
| 检索 hit@1（40 题） | 87.5% | 80.0% |
| 检索 hit@5（40 题） | 97.5% | 97.5% |
| 单次延迟 | ~800ms（外部 API） | ~600ms（本机 CPU） |

结论：本地重排零外部依赖、可离线，但质量略降（-7.5pp hit@1），延迟收益有限。
默认使用 LLM 重排；ag.rerank.provider=local 一键切换离线模式。
